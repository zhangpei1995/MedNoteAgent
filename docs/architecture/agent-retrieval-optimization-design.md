# Agent 检索与推理优化设计

本文定义 MedNoteAgent 在药品说明书问答中的低延迟、高证据质量链路。目标不是让大模型承担所有推理，而是采用分层检索和分级推理：便宜、确定性的步骤尽量前置，昂贵模型只在必要时调用。

## 1. 设计目标

1. 常规说明书查询在毫秒级完成证据召回。
2. 自然语言问法通过轻量规划和混合检索提升召回质量。
3. 高风险或低置信度问题才升级到重排和更强回答模型。
4. 医学结论始终以说明书证据为边界，模型不直接生成无证据结论。
5. 检索、重排、模型规划和回答生成通过接口隔离，便于替换本地实现或云端模型。

## 2. 总体链路

```text
用户问题
  -> 规则/词典快速解析
  -> 小模型结构化规划（可选）
  -> 多路召回：关键词 + 结构化过滤 + 语义召回
  -> RRF 融合排序
  -> 条件触发 reranker
  -> 证据充足性和风险判断
  -> 基于证据生成答案
```

外部 API 仍只接收用户自然语言问题。意图、药品名、章节、风险信号、查询改写和检索模式都属于 Agent 内部上下文。

## 3. 三档执行模式

| 模式 | 适用场景 | 链路 | 目标 |
| --- | --- | --- | --- |
| `FAST` | 明确药品名和章节，如“二冬汤颗粒怎么吃” | 规则规划 + 关键词/BM25 + 药品/章节过滤 | 最快命中确定证据 |
| `BALANCED` | 默认模式，自然语言问法或章节不明确 | FAST + 语义召回 + RRF 融合 | 速度和召回质量均衡 |
| `ACCURATE` | 合并用药、特殊人群、禁忌、低置信度 | BALANCED + reranker + 更严格风险判断 | 降低漏召回和误排序 |

当前本地实现不直接接入外部模型，而是先提供可替换接口和 fixture 策略。后续可把 `BALANCED` 的语义召回替换为 embedding 检索，把 `ACCURATE` 的重排替换为云端或本地 reranker。

## 4. 模型使用原则

### 4.1 Query 侧规划模型

Query 侧模型只输出结构化规划，不生成医学结论。

推荐输出字段：

```json
{
  "intent": "CONTRAINDICATION",
  "drugNames": ["菖麻熄风颗粒"],
  "sections": ["禁忌", "注意事项"],
  "riskSignals": ["过敏"],
  "keywords": ["菖麻熄风颗粒", "禁忌", "过敏", "慎用"],
  "rewrittenQuery": "菖麻熄风颗粒 禁忌 过敏 慎用"
}
```

模型选择建议：

| 任务 | 建议 |
| --- | --- |
| 规则能覆盖的明确问题 | 不调用模型 |
| 意图识别、实体抽取、query 改写 | `qwen-turbo` 或本地 `Qwen3-0.6B/1.7B-Instruct` |
| 多轮省略、复杂合并用药规划 | `qwen-plus` 或同级模型兜底 |

### 4.2 数据侧关键词

数据入库时关键词不应完全依赖生成模型，应优先来自：

1. 药品名、成分、规格、批准文号和生产企业。
2. 说明书章节标题。
3. 医学风险词典，如禁忌、过敏、孕妇、儿童、老人、肝肾功能、合并用药。
4. 章节内容分词和 BM25 token。
5. 可选模型补充的同义表达。

### 4.3 Embedding 和 Reranker

后续可替换为：

| 能力 | 起步模型 |
| --- | --- |
| 向量召回 | `Qwen3-Embedding-0.6B` 或云端 embedding 服务 |
| 证据重排 | `Qwen3-Reranker-0.6B`，只对 top 20-30 使用 |

## 5. 检索融合策略

多路召回结果使用 RRF（Reciprocal Rank Fusion）融合，避免手动把 BM25 分数、语义分数和图谱分数硬相加。

```text
finalScore = Σ weight_i / (k + rank_i)
```

默认 `k=60`。关键词、语义、结构化过滤和重排都可以作为一路 rank list 参与融合。

## 6. 升级条件

默认先尝试 FAST。当出现以下情况时升级到 BALANCED：

1. 未明确命中药品名。
2. 未明确命中章节。
3. FAST 候选不足。
4. 用户问题包含自然语言同义表达。

出现以下情况时升级到 ACCURATE：

1. 风险等级为 `HIGH`。
2. 问题涉及合并用药、相互作用、孕妇、儿童、老人、肝肾功能异常。
3. top 结果分差过小。
4. 检索结果跨多个药品且无法确定目标药品。
5. 证据不足但用户要求明确用药建议。

## 7. 代码边界

按当前业务模块化结构落地：

| 能力 | 包位置 |
| --- | --- |
| 请求规划 | `agent/planning` |
| Agent 证据召回接口和策略 | `agent/retrieval` |
| 知识证据模型 | `knowledge/evidence` |
| SQLite/FTS/向量存储实现 | `persistence/store/knowledge` |

`DrugKnowledgeSearchTool` 只依赖稳定的 `EvidenceRetriever`。内部可以替换为 FTS、embedding、reranker 或图谱检索，不能把具体检索技术泄漏到 Agent 主流程。

## 8. 评估指标

每次优化检索或规划能力时至少关注：

1. `Recall@5`：答案所需证据是否在前 5 条。
2. `MRR`：第一条正确证据排名。
3. 平均检索耗时和 P95 耗时。
4. 高风险问题的证据缺失率。
5. 最终回答是否超出证据范围。

短期以 fixture eval 保证链路正确；中期补充 100-300 条说明书问答评测集。
