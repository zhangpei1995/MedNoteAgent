# Agent 协作手册

本文档用于约束后续 Agent 或开发者在 MedNoteAgent 项目中的工作方式。核心目标是：先理解边界，再做最小改动；通过清晰接口和模块扩展能力，而不是在现有类里持续堆代码。

执行任务前必须同时阅读根目录 `AGENTS.md` 和 [工程开发约定](development-conventions.md)。P0 规则以 `AGENTS.md` 为准，技术栈、DAO、存储、工具库和删除清理细节以工程开发约定为准。

## 基本原则

- 不随意扩展项目范围。任何新增能力都应服务于当前需求、现有 Agent 链路或明确的下一阶段目标。
- 不做大面积重构。除非任务明确要求，否则只修改与当前问题直接相关的文件。
- 不把临时 demo 写成长期架构。占位实现可以存在，但必须放在清晰的 `impl`、`mock` 或 demo 边界内。
- 不让控制器、Agent 编排器或工具类承载过多职责。一个类只负责一个稳定角色。
- 优先维护现有包结构、命名方式、接口边界和测试风格。
- 新功能按当前目标设计，不兼容未被需求明确要求的历史代码、旧写法或旧行为。
- 删除老功能或核心代码时，必须检查调用关系、残留文件、配置、测试和文档引用，并清理干净。
- 医学问答相关改动必须保留证据来源、风险提示和可追溯性，不能只追求回答流畅。

## 技术栈约定

项目工程选型固定如下，详细规则见 [工程开发约定](development-conventions.md)：

| 层次 | 约定 |
| --- | --- |
| 应用框架 | Spring Boot 3。 |
| 底层存储 | 暂时使用 SQLite。 |
| DAO 层引擎 | 使用 MyBatis Plus。 |
| 常用工具 | 使用 `hutool-all`。 |

不得绕开这些约定另起一套持久化、DAO 或常用工具方案；确需新增依赖时，必须在计划中说明现有技术栈为什么不能满足需求。

## 项目检索方式

修改代码前必须先做定向检索，避免凭感觉扫项目或盲改。

1. 优先使用 codegraph 定位相关类、接口、调用关系和模块边界。
2. 再使用 `rg`、`rg --files` 等工具做小范围文本补充。
3. 不要大量打开无关文件，不要全文扫描整个项目后再决定方向。
4. 如果只需要确认一个接口或类的职责，优先阅读 `package-info.java`、接口定义、测试和最近的调用点。
5. 读代码时按调用链收敛：入口、接口、实现、测试，不做无目的横向扩散。
6. 修改 README、目录树、阅读顺序、文档索引或链接清单前，必须用真实文件列表校验每个条目。

推荐检索顺序：

```text
需求关键词
-> codegraph 查找相关符号和调用关系
-> rg 精确查找类名、接口名、配置项或接口路径
-> 阅读最小必要文件
-> 制定最小修改方案
```

## 模块职责

当前项目的模块边界应保持清晰：

| 模块 | 职责 |
| --- | --- |
| `controller` | HTTP 入参出参、接口编排和展示，不承载业务规则。 |
| `agent` | Agent 总体编排、会话流程和运行时决策，不直接写具体医学逻辑。 |
| `agent.tool` | 计划中的工具契约、工具描述、工具注册和具体工具适配；引入前不得在文档中写成已实现。 |
| `agent.runtime` | 计划中的工具调用记录、运行状态、失败类型和会话审计；引入前不得在文档中写成已实现。 |
| `service.spi` | 可替换能力接口，例如规划、检索、风控、回答生成。 |
| `service.impl` | 当前接口的 demo 或本地实现，可被真实模型、检索服务或策略服务替换。 |
| `domain` | 领域对象和核心概念，避免掺入框架或接口展示逻辑。 |
| `dto` | API 请求响应结构，不承载业务决策。 |
| `config` | Spring 配置、外部客户端配置和环境变量装配。 |

新增文件前先判断它属于哪个职责层。无法归类通常说明设计还没有收敛，应该先拆清职责，而不是新建一个含糊的 `manager`、`helper` 或 `util`。

## 扩展方式

新增能力优先通过接口、注册机制、工厂模式或策略模式扩展，而不是改大类、堆分支。

- 新增可替换业务能力时，先定义或复用 `service.spi` 接口，再在 `service.impl` 提供实现。
- 新增 Agent 工具层时，先定义工具契约、工具元数据和注册机制，再接入具体工具实现；只有相关类型真实存在后，README 和索引才能描述其已实现能力。
- 新增多种同类实现时，使用工厂、策略映射或 Spring 注入集合选择实现，不在调用方写长串 `if/else`。
- 新增外部模型、检索源或安全策略时，适配层放在实现类内，调用方只依赖接口。
- 新增配置项时，集中放入配置类和 `application.yml`，不要把魔法值散落在业务代码中。
- 新增数据结构时，优先复用已有 `domain` 或 `dto`；确实需要新类型时，命名要表达业务含义。

禁止的扩展方式：

- 在 Controller 中直接拼接 Agent 逻辑、检索逻辑或医学规则。
- 在 `MedNoteAgent` 中不断增加专用分支，让编排器变成业务容器。
- 把多个工具的输入输出混在一个大 Map 里长期传递。
- 为一次性需求创建泛化过度的抽象。
- 为绕过边界而新增 `CommonUtil`、`AgentUtils` 这类难以维护的万能类。

## 代码组织要求

- 一个文件只表达一个主要概念，文件名与类名、职责保持一致。
- 包内类的角色要能从名称看出来，例如 `Planner`、`Retriever`、`Assessor`、`Generator`、`Registry`、`Store`。
- 接口命名表达能力，避免表达实现细节。
- 实现类命名表达来源或策略，例如 `RuleBasedRequestPlanner`、`MedicalRiskAssessor`。
- 方法保持短小，复杂流程拆成有业务含义的私有方法或独立协作者。
- 日志、审计和错误信息要帮助排查工具链路，不能吞掉失败。
- 注释只解释边界、约束和非显然原因，不重复代码字面意思。

## 修改流程

每次修改建议按以下流程执行：

1. 明确本次任务的最小交付目标。
2. 用 codegraph 定位相关符号、调用关系和边界。
3. 用 `rg` 精确补充配置、测试和接口路径。
4. 判断应修改的模块和不应触碰的模块。
5. 先改接口或契约，再改实现，最后改入口和测试。
6. 运行与改动范围匹配的测试。
7. 如果删除了旧功能，回看是否还有残留类、方法、参数、配置、依赖、测试、脚本和文档引用。
8. 回看文件数量、职责边界和命名是否仍然清晰。
9. 运行 `codegraph sync` 更新索引。

## 合并后复查

合并、变基或解决冲突后，优先检查 README 和文档索引是否被旧分支内容覆盖。必须确认冲突标记、文档路径、接口路径、类名、注解和配置项都能在当前代码或真实文件列表中找到；找不到的旧说明应删除或明确标注为后续计划。

## 测试与验收

涉及 Agent 链路、工具选择、检索、风控或回答生成时，应优先补充或更新测试，而不是只靠手动调用接口。

最低验收标准：

- 改动能通过相关单元测试或集成测试。
- 新增工具能在工具列表中被描述和选择。
- 工具失败有明确失败类型、上下文或审计记录。
- 医学回答仍包含证据引用和必要风险提示。
- 新增模块没有破坏 `controller`、`agent`、`service.spi`、`service.impl` 的职责分离。
- 文档或注释同步说明新增扩展点的使用方式。

## Agent 自检清单

提交或结束任务前，Agent 应自问：

- 我是否先用 codegraph 定位，而不是大量扫描项目？
- 本次改动是否只覆盖当前需求需要的范围？
- 有没有把业务规则塞进 Controller 或编排器？
- 有没有通过接口、工具契约、工厂或策略扩展？
- 有没有新增含糊的万能类、万能方法或万能 Map？
- 文件和模块名称是否能准确说明职责？
- 测试是否覆盖了本次行为变化？
- 如果删除了老功能，是否已经清掉残留文件、配置、测试和文档引用？
- 是否遵守 Spring Boot 3、SQLite、MyBatis Plus、`hutool-all` 的项目技术栈约定？
- 对医学安全、证据追溯和失败审计是否没有退化？

如果以上任一问题回答不清楚，应先收敛设计，再继续写代码。
