# 工程开发约定

本文档用于框定 MedNoteAgent 的技术栈、代码组织、删除清理和依赖选择规则。Agent 执行任务前应先阅读根目录 `AGENTS.md`，再阅读本文档和 `agent-handbook.md`。

## 技术栈边界

项目技术选型以当前新功能目标为准，不为了兼容旧写法引入额外框架或重复能力库。

| 层次 | 约定 |
| --- | --- |
| 应用框架 | Spring Boot 3。 |
| 底层存储 | 暂时使用 SQLite。 |
| DAO 层引擎 | 使用 MyBatis Plus。 |
| 常用工具 | 使用 `hutool-all`。 |
| API 文档 | 使用项目已接入的 Knife4j / OpenAPI 方案。 |
| 外部模型客户端 | 保持在明确的 client/config 边界内，不向 Controller 或 DTO 泄漏。 |

新增依赖前必须先判断现有技术栈是否已经覆盖需求。除非计划中说明原因并经过 Review，不新增与以上能力重叠的替代框架，例如另一个 DAO 框架、另一个通用工具库或另一套配置装配方式。

## 新功能设计规则

- 先分析当前目标、输入输出、数据流、边界、失败场景和验收标准，再决定代码结构。
- 新功能默认不兼容未被需求明确要求的历史代码、旧字段、旧接口或旧行为。
- 不为了显得“稳妥”而保留双路径逻辑、历史兜底分支、废弃字段或无调用方的适配层。
- 如果同一能力会有多种实现，先定义接口或策略契约，再提供具体实现。
- 如果只有一个明确实现，不要提前创建空泛抽象；等出现稳定变化点再抽象。

## DAO 与存储约定

- 数据访问代码归入清晰的 DAO / mapper 边界，业务层不直接拼 SQL。
- 使用 MyBatis Plus 承载基础 CRUD、分页和条件构造；复杂查询需要说明查询目的和索引/性能考虑。
- SQLite 是当前临时底层存储，SQL、字段类型和迁移脚本应避免绑定其他数据库的专有能力。
- Entity、Mapper、Service、DTO 的职责要分清：Entity 面向持久化，DTO 面向接口入参出参，Service 承载业务编排。
- 新增表、字段或索引时，同步更新初始化脚本、配置、测试数据和相关文档。

## 工具库使用规则

- 常用字符串、集合、日期、校验、文件等工具优先使用 JDK 标准库或 `hutool-all`，不要再引入重复工具库。
- Hutool 只能用于明确的通用能力，不应掩盖业务语义；关键业务判断仍要放在有业务命名的方法或类中。
- 不新增万能 `Util`、`Helper`、`Manager` 类承载长期业务逻辑。

## 删除与清理规则

删除老功能、旧入口或核心代码时，必须把删除当成一次完整变更，而不是只删当前报错点。

检查顺序：

1. 用 CodeGraph 查看被删符号的 callers、callees 和 impact。
2. 用 `rg` 检查类名、方法名、配置项、接口路径、表名、字段名和文档引用。
3. 删除或更新残留的 Controller 入口、Service 实现、Mapper、DTO、配置、测试、脚本、示例和文档。
4. 移除不再需要的依赖、配置属性、测试夹具和 README/索引条目。
5. 运行匹配范围的测试或至少执行能覆盖该变更的检查。
6. 完成后运行 `codegraph sync`。

不得留下：

- 无调用方的旧类、旧方法、旧参数或旧配置。
- 指向已删除能力的 README、文档索引、接口示例或测试数据。
- 为了“以后可能用”保留的死代码、注释块或废弃分支。

## 文档对齐规则

- 文档必须描述当前项目真实状态或明确标注为计划项。
- README、目录树、推荐阅读顺序、文档索引和交叉引用必须用 `rg --files` 或等价方式校验真实文件存在。
- 新增或删除工程能力时，代码、配置、测试、文档和 CodeGraph 索引要一起对齐。
