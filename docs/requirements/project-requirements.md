# MedNoteAgent 项目需求文档

## 1. 项目概述

MedNoteAgent 是一个面向药品说明书知识管理和智能问答的 Agent 项目。项目目标是将药品说明书 PDF 转化为可检索、可追溯、可推理的知识库，并基于说明书原文证据回答用户关于药品禁忌、用法用量、不良反应、药物相互作用、特殊人群用药和药理作用等问题。

项目不是做一个普通聊天机器人，而是做一个“以药品说明书为证据边界”的医学问答系统。系统回答必须尽量来源于已入库说明书，不能脱离证据给出确定性医疗建议。

## 2. 要解决的问题

当前药品说明书通常以 PDF 或非结构化文本形式存在，直接阅读和检索效率低。用户在实际使用中常见的问题包括：

1. 想快速知道某个药是否有禁忌、注意事项或不良反应。
2. 想判断两个药或多个药是否可能存在相互作用。
3. 想了解孕妇、儿童、老人、肝肾功能异常患者等特殊人群是否适合使用某药。
4. 想根据症状、疾病或用药场景定位说明书中的相关依据。
5. 想得到可信、可追溯、有风险提示的回答，而不是没有来源的模型生成内容。

MedNoteAgent 需要解决的核心问题是：

```text
非结构化说明书 PDF
  -> 转换为结构化知识和证据片段
  -> 建立检索、图谱和模型问答链路
  -> 输出有证据、有边界、有风险提示的医学回答
```

## 3. 建设目标

### 3.1 总体目标

建设一个以药品说明书为基础的医学知识 Agent，支持说明书入库、知识抽取、证据检索、风险评估和基于证据的问答生成。

### 3.2 阶段目标

| 阶段 | 目标 | 说明 |
| --- | --- | --- |
| 第一阶段 | 完成项目基础架构 | 建立 Agent、Client、Handler、Service、Repository、Strategy 等分层结构 |
| 第二阶段 | 完成 PDF 说明书入库 | 支持解析 PDF、清洗文本、识别章节、生成证据片段 |
| 第三阶段 | 完成基础问答链路 | 支持基于说明书证据回答禁忌、注意事项、不良反应等问题 |
| 第四阶段 | 建立结构化知识和图谱 | 抽取药品、成分、禁忌、相互作用、特殊人群等实体关系 |
| 第五阶段 | 强化安全和质量控制 | 增加风险评估、证据校验、回答校验和审计追踪 |

## 4. 核心工作内容

### 4.1 说明书入库

系统需要支持将药品说明书 PDF 导入知识库。入库过程包括：

1. 读取说明书文件。
2. 提取 PDF 文本、页码、段落和表格信息。
3. 清洗页眉、页脚、目录、乱码、重复文本和异常换行。
4. 识别说明书标准章节，例如药品名称、成分、功能主治、用法用量、不良反应、禁忌、注意事项、药物相互作用、药理毒理等。
5. 按章节和语义切分证据片段。
6. 抽取药品、成分、适应症、禁忌对象、不良反应、特殊人群和相互作用等结构化信息。
7. 写入原文证据库、结构化知识库、向量索引和知识图谱。
8. 生成入库质量报告，记录缺失章节、解析质量、抽取置信度和来源信息。

### 4.2 知识建模

系统需要围绕说明书建立双层知识结构：

```text
第一层：原文证据片段
  - 保留说明书原文、章节、页码、来源文件和片段 ID
  - 作为回答引用和可信度校验的基础

第二层：结构化实体关系
  - 药品、成分、禁忌、相互作用、特殊人群、不良反应等节点
  - 节点和关系必须绑定至少一个原文证据片段
```

这种设计可以同时满足语义检索、结构化推理和证据追溯。

### 4.3 Agent 问答

用户提问后，系统需要完成完整的问答推理链路。外部入口只接收用户自然语言问题；任务主题、说明书检索范围、意图、关键实体和风险信号均由 Agent 内部规划生成，不要求用户额外传入。

```text
用户问题
  -> 参数校验
  -> 问题标准化
  -> 内部任务主题生成
  -> 意图识别
  -> 药品、成分、症状、特殊人群识别
  -> 查询改写
  -> 混合检索
  -> 证据聚合与排序
  -> 证据充足性判断
  -> 医学风险评估
  -> 回答生成
  -> 回答校验
  -> 返回最终答案和证据来源
```

系统应优先支持以下问题类型：

| 问题类型 | 示例 |
| --- | --- |
| 禁忌查询 | 这个药哪些人不能吃？ |
| 不良反应 | 吃这个药可能有哪些不良反应？ |
| 用法用量 | 这个药说明书推荐怎么用？ |
| 药物相互作用 | 这个药能和另一个药一起吃吗？ |
| 特殊人群 | 孕妇、儿童、老人能不能用？ |
| 药理作用 | 这个药的药理作用是什么？ |
| 说明书基础信息 | 成分、规格、批准文号、生产企业是什么？ |

### 4.4 模型服务封装

项目当前已引入 DashScope 千问 SDK，并存在 `QianwenClient`。后续需要将模型调用抽象为统一 `ModelClient` 接口，使业务层不直接依赖具体模型 SDK。

模型服务需要支持：

1. 单轮问答。
2. 多轮上下文问答。
3. 系统提示词配置。
4. 模型名称配置。
5. 异常统一转换。
6. API Key、接口地址和超时时间配置化。

### 4.5 风险评估与安全控制

医学问答必须采用保守策略。系统需要识别高风险问题，并改变回答方式。

高风险场景包括：

1. 用户询问是否可以合并用药。
2. 问题涉及孕妇、儿童、老人、哺乳期、肝肾功能异常等特殊人群。
3. 命中禁忌、慎用、严重不良反应、药物相互作用等说明书章节。
4. 用户描述疑似严重不良反应或急症。
5. 检索证据不足但用户希望获得明确用药建议。

风险等级建议分为：

| 风险等级 | 含义 | 回答要求 |
| --- | --- | --- |
| LOW | 常规信息查询 | 正常回答并提供证据 |
| MEDIUM | 需要谨慎解释 | 增加限制条件和注意事项 |
| HIGH | 涉及禁忌、冲突或特殊人群 | 明确风险、避免替代医生判断 |
| UNKNOWN | 信息不足无法判断 | 说明证据不足并追问关键信息 |

### 4.6 回答质量校验

系统输出前需要检查回答是否符合以下要求：

1. 是否引用了说明书证据。
2. 是否出现证据中没有的药名、剂量、禁忌或结论。
3. 高风险问题是否包含安全提示。
4. 证据不足时是否避免确定性结论。
5. 是否暴露系统 Prompt、内部调试信息或敏感配置。
6. 是否给出超出说明书依据的医疗诊断或处方建议。

## 6. 非功能需求

| 类型 | 需求 |
| --- | --- |
| 准确性 | 回答必须基于说明书证据，不能凭空生成医学结论 |
| 可追溯性 | 每个重要回答结论都应能追溯到药品、章节、证据片段和来源文档 |
| 可扩展性 | 模型、PDF 解析器、检索方式、图数据库和向量库都应可替换 |

| 安全性 | 不提交真实 API Key，不输出敏感信息，不替代医生诊断 |

| 稳定性 | 外部模型调用、文件解析和索引写入失败时应有明确异常和重试策略 |

## 7. 核心难点与处理方案

### 7.1 PDF 解析质量不稳定

难点：

PDF 可能存在扫描件、表格错位、换行异常、页眉页脚重复、章节标题不规范等问题，直接抽取容易造成文本混乱。

处理方案：

1. 解析后同时保留原始文本和清洗文本。
2. 清洗过程保留页码映射，不能破坏证据追溯。
3. 章节识别采用“规则优先、模型兜底”的方式。
4. 对解析质量进行评分，低质量文档进入人工复核或二次处理流程。

### 7.2 医学回答不能依赖模型自由发挥

难点：

大模型可能生成看似合理但没有说明书依据的内容，医学场景中这种幻觉风险较高。

处理方案：

1. 回答生成前必须先检索证据。
2. Prompt 中明确要求只基于给定证据回答。
3. 输出前进行回答校验，检查是否超出证据范围。
4. 证据不足时返回“不足以判断”，并提示需要补充的信息。

### 7.3 药物相互作用和药理冲突复杂

难点：

相互作用不一定只发生在药品名称层面，也可能发生在成分、药理作用、代谢机制或特殊人群条件下。

处理方案：

1. 建立药品、成分、相互作用事件和证据片段之间的关系。
2. 不把相互作用简化为两个药之间的一条边，而是使用 `DrugInteraction` 事件节点承载风险等级、机制和建议。
3. 对无法确认的合并用药问题采用保守回答，建议咨询医生或药师。

### 7.4 结构化抽取存在歧义

难点：

说明书中常出现“尚不明确”“慎用”“未进行该项实验”“遵医嘱”等模糊表达，不能简单转换为确定性结论。

处理方案：

1. 实体和关系增加置信度字段。
2. 区分禁用、慎用、注意、未知等不同语义。
3. 模型抽取必须返回 JSON，并包含证据原文。
4. 低置信度结果不直接用于高风险确定性回答。

### 7.5 系统分层容易变复杂

难点：

说明书入库和问答流程步骤较多，如果全部写在 Service 或 Agent 中，代码会快速膨胀，难以测试和维护。

处理方案：

1. Agent 只负责任务编排入口。
2. 聚焦但复杂的流程使用 Handler 承载，例如 `InstructionIngestionHandler`、`MedicalQuestionAnswerHandler`、`KnowledgeGraphWriteHandler`。
3. 外部模型调用封装在 Client 层。
4. 可替换算法放入 Strategy 层。
5. 数据访问统一放入 Repository 层。

## 8. 目标效果

项目完成后，应达到以下效果：

1. 用户可以导入药品说明书 PDF，系统自动解析并形成可检索知识。
2. 用户可以用自然语言提问药品相关问题。
3. 系统能够从说明书中召回相关证据，并给出清晰回答。
4. 回答包含结论、依据、风险提示、可执行建议和证据来源。
5. 对禁忌、合并用药、特殊人群等高风险问题，系统能够保守处理。
6. 当知识库证据不足时，系统不会强行回答，而是说明缺少依据。
7. 开发层面形成清晰分层，后续可以逐步替换模型、检索引擎、图数据库和 PDF 解析组件。

示例回答结构：

```text
结论：
根据当前说明书证据，暂不建议直接判断该情况可以用药。

依据：
说明书“禁忌”章节提到……
说明书“注意事项”章节提到……

风险提示：
该问题涉及特殊人群或合并用药，存在较高风险。

建议：
请补充年龄、既往疾病、正在使用的其他药物，并咨询医生或药师。

证据来源：
药品名称 / 说明书文件 / 章节 / 页码 / 证据片段 ID
```

## 9. 边界说明

本项目应明确以下边界：

1. 系统提供的是基于说明书的用药信息辅助查询，不替代医生诊断和处方。
2. 系统不能在证据不足时给出确定性医疗建议。
3. 系统不应输出超出已入库说明书范围的医学结论。
4. 系统初期以药品说明书为核心知识来源，不默认接入临床指南、论文或互联网搜索。
5. 系统需要保护用户隐私和密钥安全，不应记录或泄露敏感信息。

## 10. 初步验收标准

| 类别 | 验收标准 |
| --- | --- |
| 文档入库 | 能成功导入至少两份药品说明书 PDF，并识别主要章节 |
| 证据追溯 | 任意回答中的关键结论都能定位到来源文件、章节和证据片段 |
| 基础问答 | 能回答禁忌、不良反应、注意事项、成分、功能主治等基础问题 |
| 风险控制 | 对特殊人群、禁忌和合并用药问题能触发风险提示 |
| 证据不足 | 检索不到充分证据时不编造答案 |
| 架构质量 | Agent、Handler、Service、Client、Repository、Strategy 职责清晰 |
| 配置安全 | API Key 和模型配置不硬编码在业务代码中 |
| 测试覆盖 | 核心解析、检索、风险判断和回答校验流程具备基础测试 |

## 11. 推荐实施顺序

1. 整理 Maven 项目结构和基础包。
2. 抽象 `ModelClient`，改造 `QianwenClient`，移除硬编码密钥。
3. 建立说明书入库领域模型和 `InstructionIngestionHandler`。
4. 完成 PDF 文本解析、清洗和章节识别。
5. 建立证据片段模型、关键词索引和基础检索能力。
6. 建立 `MedicalQuestionAnswerHandler`，打通基础问答链路。
7. 增加风险评估、回答校验和证据不足处理。
8. 增加结构化抽取和知识图谱写入。
9. 补充测试、日志、异常处理和入库质量报告。
